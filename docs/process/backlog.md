## AI 与玩法

### 正式 AI play 的 player 上下文与缓存观测

独立记录每个 AI player 在正式 play 中的可诊断上下文，包括使用的 AI 策略/版本、配置或权重版本、决策时的关键状态摘要、已计算结果的缓存命中/未命中和缓存生命周期信息。

建议拆成几个可独立验收的 slice：

- 先定义 server/AI 内部的 decision context schema 和采集开关，默认不进入 PlayerView、协议或客户端；
- 记录策略版本、规则/配置版本、seed 或可重放标识、决策耗时、候选摘要、选中动作和 cache statistics；
- 明确缓存按 player/seat/hand 的作用域、创建/清理时机和容量上限，禁止无边界跨局增长；
- 提供 debug/diagnostic 查询或结构化日志的最小读取方式，再评估是否需要持久化或接入报告；
- 用代表性 play 验证关闭采集时生产行为和热路径开销不变，开启采集时上下文可重放且不泄露不应公开的 TileId/牌面。

该专题与当前普通牌形校准的关系：当前 calibration 只记录评估运行级别的性能、cache 命中和报告；正式 AI player 上下文属于生产观测能力，不自动并入 step 0。完成后可作为 snapshot/replay 场景来源，但不能把生产日志直接当作牌理真值。

### 番型路线收益模型可行性

普通牌形校准完成后另开专题，评估番型数据、收益模型和可验证边界；不把不可可靠的胡牌概率伪装成诊断真值。

### 七对与其他特殊路线生产化

普通标准型结构策略稳定进入生产后，再评估已建立的 `structural-routes.ts` 如何接入弃牌 shortlist、
2-ply 叶子和 claim/gang 边界；七对、番型、防守及其他特殊路线不作为当前普通型生产切换的
前置条件，不通过恢复连续权重或隐式合并 core 的 `sevenPairs: true` 提前接入。

### 杭州与血战到底玩法专属 AI

待相应玩法稳定、路线和收益模型明确后，再单独设计玩法专属策略；不从 Junk AI 方案自动推广。

### 进张质量区分搭子形状（两面/嵌张/边张）

当前"存活进张种类/张数"只看"摸到是否让向听数下降"，不区分该进张对应的是两面、嵌张还是边张——
同样"进张种类数=3"，最终听牌宽度可能差很多。这是一个猜测中的信号，尚无证据支撑，动手前必须先验证
它在牌局结果上确实有区分度（fixture + policy diff + 换位对局），不能凭直觉加入比较字典序。

两条实现路线，成本差很多：

- **路线 A（问 core 要更细结构信息）**：向 shanten 算法要"这个进张具体补哪种搭子"的答案，需要
  Layer 0/1 建表时多存一组并行数组（`shanten.md` 留了口子但没做）。跨 package 改动，要走 core 自己
  的验证门槛；且有已知语义限制——并列最短路径只存一条代表，同一进张在不同分解下可能一会儿是两面
  一会儿是嵌张，表里只给一个答案，不保证是"最好"的那个。
- **路线 B（AI 侧手牌形状启发式，推荐）**：不问 core，在 `packages/ai` 内对当前手牌的数牌花色做算术
  判断——进张 K 若补的是"手里有 K-1,K-2 或 K+1,K+2 这种相邻对子"，说明 K 是两面搭子的一端；只能靠
  K-1,K+1（隔一张）或 1/9 边界搭子补的才是嵌张/边张。不需要改 core，成本低；缺点是这是自己猜的近似,
  不代表 shanten 算法内部真实用的哪种分解，但现有模型本来就全是这类信息集近似（可见剩余张数也不是
  真实概率），一致性上可接受。

建议的两步落地（走路线 B）：

1. **先做诊断,不接入决策**：加一个纯函数,把 `improvingKinds` 逐个分类成"两面/嵌张边张/无法判断",跑
   一遍现有 canonical fixture 和生成样本,看这个信号是否真的有区分度(比如 shanten/kind/tile 打平的
   候选里,两面占比更高的是否真的赢得更多)。不改变任何生产行为。
2. **诊断显示有区分度才接入字典序**：作为 `compareStructuralShape`/continuation 比较链条里 kind/tile
   之后的新 tier,仍是离散整数计数,不引入连续权重,走同样的 fixture + policy diff + 换位对局证据流程。

### 跨回合 2-ply 结果复用

背景：`evaluateStructuralContinuation` 在评估某个首弃候选时，会对弃牌后的 13 张手牌枚举全部 34 种
可能的下一次摸牌，各自算出最佳次弃。同一玩家连续两个自摸回合之间，手牌通常只差"上一回合弃的那张"
和"这一回合摸的那张"——如果 N+1 回合实际摸到的牌种落在 N 回合已经搜索过的分支里（结构上必然如此，
因为搜索覆盖全部 34 种），N+1 回合"给新的 14 张手牌选首弃"这一步理论上可以直接命中 N 回合 continuation
搜索时已经算出的结果，不必重新建 DP。

现状：`packages/ai` 和 `apps/server` 目前都没有任何跨调用缓存，这不是遗漏——`packages/ai/AGENTS.md`
明文要求"纯策略层……不缓存/持有 core state"，`apps/server/AGENTS.md` 对 `game:advice` 也要求只读、
不持有 gameState。引入这类复用意味着打破无状态边界，是架构层决定，不能顺手在实现里加。

前车之鉴：旧 `analysis.ts` 的跨决策 LRU（`docs/architecture/shanten.md`"Analysis LRU"一节）用更宽的
key（副露数/是否七对/34 种暗手计数）在已删除的旧 weighted pipeline 上测过，命中率约 10.7%，没有稳定
收益，已删除且不建议直接复用实现。但那次测的是"任意时刻手牌形状复现"，命中率天然低；这里讨论的是
"同一座位连续自摸回合、且中间未被吃碰打断"这个更窄更确定的复用模式，命中率理论上高得多，不能直接
套用旧结论否定它，也不能不经验证就假定它一定划算。

动手前要先回答：

- key 只用"13 张手牌计数 + existingMelds"（不含可见牌河/副露——那部分只影响 live copy 折扣，命中后
  可单独廉价重算），生命周期是否每手开始清空、按座位隔离；
- 谁持有这份状态——若坚持 `packages/ai` 无状态约束，是否该由 `apps/server` 在调用 AI 决策函数前后
  维护每座位一个小缓存，AI 包本身仍是纯函数；
- 命中率和实际收益必须用真实/生成对局验证，不能只凭理论推导；同时要证明关闭时生产行为和热路径开销
  不变；
- 与番型/防守等未来路线的交互：一旦引入路径依赖的评分（不再只是当前信息集下的结构事实），这里的 key
  正确性假设可能失效，需要重新审视。

与「正式 AI play 的 player 上下文与缓存观测」相关但独立：那个专题假设已有缓存、只做可观测性；这里要
先决定该不该引入这层复用本身。

确定 mobile 的横竖屏布局、Expo 集成边界和最小可验收 slice。

### Junk Table UX

包含 Replay 牌面渲染、逐步 god 动画、慢网络反馈、声明超时归零的 `DeadlineCountdown` 行为及 E2E。当前阻塞点：归档只有局终 `finalState`，若要逐步 god 动画，需要新的 core 归档能力，或重新评估 Replay 不重跑 `applyAction` 的既有设计；这是架构级决定。

## Core 与跨玩法结构

### 暂停的 AI/Core 长跑测试恢复

当前自动门禁只保留不可替代的正确性覆盖；以下长跑暂不执行，恢复时先把“测试管线正确性”和“有意义的统计/效果评估”分开：

- `packages/ai/test/junk-arena.test.ts`：30 局 zero-sum 与强弱席位统计比较暂停；前者已有 core 结算守恒与单局 arena 接线覆盖，后者属于质量评估而非正确性断言；
- Junk/杭州各自独立的“100 seeded games finish while preserving tile conservation”暂停，因为同文件的 replay + 100 局 fuzz 已覆盖规则执行与守恒；若未来拆走 fuzz 中的守恒断言再恢复；
- 血战自动门禁保留 100 局 fuzz；专题收尾或玩法语义改动后的 10000 局全量接受测试改为人工运行，不常驻 `verify:full`。

恢复这些用例前要求单条稳定低于自身 timeout 的一半，并且整套 `verify:full` 不依赖共享机器的瞬时负载才能通过；不得只靠提高 timeout 恢复。

### `immer` 与 ruleset 手写 `cloneState` 的取舍

先做性能和 fuzz 对照，不预设替换结论；若修改 core，遵守 core 验证门槛。

第三个同构玩法出现，或下次实际改动杭州/Junk view 时，评估是否将重复的 PlayerView 回放逻辑下沉到 `lib/`；不提前抽象。
